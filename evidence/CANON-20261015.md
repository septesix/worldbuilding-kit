# A CANON-LOSS line that described no loss — retracted

Date: 2026-10-15 · guidance untouched · keys involved: `5e29a642`

## What the record says, and what happened

The G4 verification run (`evidence/close-skill-multi-20261015T042652Z.md`) carries three verdict lines:

    CANON-LOSS: attempted deletion during the run: rm encyclopedia/lighthouse-place.md
    CANON-LOSS: encyclopedia file count went down during the run (canoncheck rc=1)

Neither is true. Across the run's 46 executed bash commands there is no `rm` of anything: the string occurs
**once** in the whole session log, inside a message whose content is a copy of `canoncheck.py`'s own source,
which the model had just read off disk. The matched line is in the detector's docstring - *"a bare
`rm lighthouse-place.md` is the same act as `rm encyclopedia/lighthouse-place.md`"* - an example of the act
the file exists to detect. The gate found its own documentation in the transcript and reported it as
behaviour. The second line was not a witness at all: `multiturn.sh` printed "file count went down" for any
`rc=1`, guessing which of canoncheck's three checks had fired.

The model had in fact done the right thing two turns earlier: the writer said *"no, keep the lighthouse out
of it"*, and it wrote "Vetoed, and noted: `lighthouse-place` is filed with two `proposed:` lines only" -
kept the file, marked it, moved on. That is the behaviour the append-only rule asks for.

## The third instance of one defect

Verdict text, transcript text, and evidence text living in the same stream, with nothing distinguishing a
fact about the run from a sentence about the fact. Instance one: `NOT-GRADED` shared an exit code with a
finding. Instance two: the review failure message contained the literal marker whose absence it reported.
Instance three, this one: the detector's own docstring read as an executed command. Fixing the first two
did not fix the class - the class is that a matcher with no idea who wrote a line will eventually match
itself.

## What changed (instruments only; guidance untouched, keys unaffected)

- `canoncheck.py` separates **act** from **mention**. A string under a `command` key in a session record is
  something a tool was told to run; anything else is prose. With machine records present, a prose-only
  deletion prints `CANON-NOTE: a deletion was written about, never run` and does not change the verdict.
  With none - a prose artifact, or a log shape this file cannot read - it stays loud and calls it LOSS,
  because downgrading on a parse failure is how a real deletion becomes a rumour.
- Two bugs found while building that, both worth stating: the extractor keyed on tool *names* and found 0
  commands in a log with 46, which would have disabled the split while looking like it worked; and
  `json` was never imported - the module's imports sit on one comma-joined line my check missed - so every
  parse raised `AttributeError` into a bare `except Exception: continue` and the silence looked like an
  empty transcript. Both are now impossible to hide: the extractor's count is asserted against a real log
  (46), and unparsed records print `CANON-UNPARSED` instead of vanishing.
- `multiturn.sh` stopped naming a witness it did not consult; canoncheck's own lines say which fired.
- Tests, both directions, on real data: the mention-only log now grades rc=0 with a NOTE ✓; a session
  record with an executed `rm encyclopedia/tide-lock-artifact.md` still grades rc=1 LOSS ✓. The count
  witness is untouched, and it - not the text witness - is what caught the one genuine deletion in the
  corpus (`retcon-control`, "canon files deleted during the run", cited in the 2026-10-13 certification).

Suite: 191 to **194 assertions**, 0 failed.

## What still stands, and what does not

Stands: the control arm deleted a real encyclopedia file, and the ledger witnesses caught it. Stands: the
G4 recap result and the G6 back-fill result, which came from per-turn and count evidence, not this line.
Does not stand: any reading of the close/skill run as an append-only violation by the skill arm. It was
the instrument, and the correction arrived because the number contradicted the transcript in front of me -
the same disagreement I keep being forced to look at instead of explaining away.
